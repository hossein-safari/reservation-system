# نیازمندی‌ها و تفسیر تصویر

این سند مبنای نسخهٔ پایه است؛ تصویر ضمیمهٔ گفتگو خوانایی کامل ندارد و فایل اصلی تصویر داخل مخزن نیست. موارد زیر **تفسیر اجرایی** هستند و ادعای رونویسی دقیق تصویر نیستند.

## نگاشت طرح تخته به مدل

| مفهوم قابل تشخیص / برداشت | مدل اجرایی | توضیح |
| --- | --- | --- |
| مشتری / کاربر | User | مشتری صاحب رزرو است؛ مدیر فضا و سانس می‌سازد. جداسازی مشتری حقیقی از حساب کاربری در آینده ممکن است. |
| بازه/سانس | Slot | شروع، پایان و قیمت روی یک فضای قابل رزرو |
| رزرو | Reservation | اتصال مشتری به سانس همراه با قیمت ثبت‌شده |
| Payment | Payment | مبلغ، وضعیت، شناسه درگاه، تاریخ |
| Transaction | Transaction | نتیجهٔ تأیید پرداخت و کد پیگیری، فقط قابل خواندن |
| BankService و Repository/Service | PaymentGateway و Repository | قرارداد مستقل از ارائه‌دهنده و زیرساخت |
| فضا یا خدمت قابل رزرو | Resource | فرض تکمیلی برای گروه‌بندی سانس‌ها؛ مانند سالن، اتاق یا میز |

## قواعد نسخه پایه

1. ثبت‌نام عمومی فقط نقش مشتری می‌سازد. مدیر با CLI ساخته می‌شود.
2. هر سانس ظرفیت یک رزرو فعال دارد. رزرو لغوشده مانع رزرو دوباره نیست.
3. سانس‌های یک فضا نباید هم‌پوشانی داشته باشند؛ بازه‌ها نیمه‌باز `[start, end)` هستند.
4. تمام زمان‌های ورودی باید timezone داشته باشند؛ ذخیره‌سازی UTC است. نمایش فارسی با منطقه زمانی تهران انجام می‌شود.
5. مبلغ عدد صحیح **ریال (IRR)** و مثبت است؛ قیمت هنگام رزرو snapshot می‌شود و از کلاینت پذیرفته نمی‌شود.
6. رزرو از `pending` به `confirmed` پس از تأیید پرداخت، یا به `cancelled` پیش از پرداخت می‌رود. رزرو تأییدشده از این مسیر لغو نمی‌شود.
7. رزرو پرداخت‌نشده به صورت خودکار منقضی نمی‌شود؛ مشتری باید آن را لغو کند. worker انقضا مرحله بعد است.
8. هر رزرو یک Payment دارد؛ تأیید دوباره همان نتیجه را برمی‌گرداند و Transaction تازه ایجاد نمی‌کند.
9. پرداخت آزمایشی فقط در محیط development/test در دسترس است؛ هیچ ارتباط بانکی و انتقال وجهی ندارد.
10. مشتری فقط رزروها و پرداخت‌های خود را می‌بیند. مدیر دسترسی مدیریت فضا/سانس دارد و با همان قوانین می‌تواند برای خودش رزرو کند.
11. فهرست‌ها صفحه‌بندی `limit/offset` دارند. شناسه‌ها UUID هستند.

## معیار پذیرش

- مدیر فضا و سانس آینده ایجاد می‌کند؛ مشتری در رابط React آن‌ها را می‌بیند.
- مشتری ثبت‌نام/ورود کرده، سانس را رزرو و درگاه آزمایشی را تأیید می‌کند؛ وضعیت رزرو و تراکنش ذخیره و در UI دیده می‌شود.
- رزرو هم‌زمان تکراری، هم‌پوشانی سانس، دسترسی به رزرو دیگری و مبلغ نامعتبر رد می‌شوند.
- مهاجرت دیتابیس، تست سرویس/API، تست رابط و build قابل تکرار هستند.

## خارج از محدوده فعلی

درگاه بانکی واقعی و callback امضاشده، refund، کد تخفیف/مالیات، ظرفیت گروهی، تقویم شمسی برای ورود تاریخ، اعلان پیامکی، بازیابی رمز، refresh token، محدودسازی نرخ توزیع‌شده، داشبورد مالی و انقضای خودکار. پیش از استفاده عملیاتی باید نیازهای واقعی این موارد مشخص و اجرا شوند.
