# ADR 0002: مرزهای بک‌اند و تفکیک هر حوزه

وضعیت: پذیرفته‌شده — ۲۰۲۶-۱۰-۲۴

## مسئله

نسخهٔ پایه، موجودیت‌ها، جدول‌ها، Repositoryها و schemaها را در فایل‌های تجمیعی نگه می‌داشت. علاوه بر دشواری تغییر هر حوزه، DomainError کد HTTP داشت، کنترلر مستقیماً به آداپتور توکن متکی بود و قرارداد UnitOfWork فقط commit داشت؛ rollback بیشتر به درخواست HTTP وابسته بود.

## تصمیم

- یک فایل برای هر موجودیت، مدل persistence و پیاده‌سازی Repository؛ ماژول‌های جدا برای سرویس، کنترلر و schema هر حوزه.
- قواعد وضعیت و اعتبارسنجی مستقل در موجودیت‌ها؛ هماهنگی و تراکنش در سرویس کاربردی.
- خطاهای دامنه بدون HTTP؛ نگاشت status فقط در api.
- قراردادهای جدا برای Repositoryها، زمان، هش رمز، توکن، درگاه و UnitOfWork.
- `ApplicationContainer` به عنوان composition root مشترک CLI و HTTP؛ هیچ import از infrastructure در api/application وجود ندارد.
- context manager تراکنش با commit در موفقیت و rollback در همهٔ شکست‌ها، شامل شکست commit.
- حفظ dataclassهای مستقل و mapping صریح SQLAlchemy در فایل هر موجودیت؛ بدون تغییر schema دیتابیس.
- تست‌های مرز وابستگی، دامنهٔ مستقل، قرارداد مشترک آداپتورها، CLI و snapshot کامل OpenAPI.

## پیامد

تغییر مدل یا query یک حوزه محل مشخص دارد و تست سرویس به دیتابیس نیاز ندارد. wiring در یک نقطه متمرکز است و تست‌ها ورود وابستگی معکوس به لایه‌های داخلی را رد می‌کنند. تعداد ماژول‌ها بیشتر شده، ولی مسئولیت هر ماژول محدود و قابل پیگیری است. enum و DTOهای مرتبط می‌توانند کنار هم باشند؛ تعداد فایل معیار کافی برای SOLID نیست.

هم‌زمانی همچنان به PostgreSQL و constraintهای دیتابیس متکی است. درگاه واقعی و refund در محدودهٔ این بازآرایی نیستند.
